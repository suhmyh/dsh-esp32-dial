# DSH ↔ ESP32 协议规范

本文档是桥接进程与固件之间的契约，以及桥接进程读取 DSH 的方式。所有字段都来自对运行中的 DSH v0.1.0-rc.6 的实测，不是猜测。

---

## 第一部分：DSH 侧（桥接进程如何读 DSH）

### 1.1 传输

DSH 的 Web API 是 **Typert RPC**，两条通道：

| 通道 | 用途 | 地址 |
|------|------|------|
| **HTTP POST** | 单次调用（查询状态） | `http://127.0.0.1:3080/api/<method>` |
| **WebSocket** | 事件推送（会话变化、审批请求） | `ws://127.0.0.1:3080/api/events.mux` |

**信任围栏**：DSH 只接受 `Host` 为环回地址、且 `Origin` 缺失或与 Host 匹配的请求。Node 的 `http.request` 默认不发 `Origin`，所以桥接进程直连即可，无需任何绕过。这与浏览器必须经过网关的原因相同。

### 1.2 请求 wire 格式

```jsonc
// POST /api/session.list
{
  "type": "client-request",
  "rpcId": "<uuid v4>",        // 每次调用新生成
  "method": "session.list",    // 必须与 URL 路径一致
  "payload": {}                // 方法参数
}
```

响应：

```jsonc
{
  "type": "server-response",
  "rpcId": "<回传同一个 uuid>",
  "result": {
    "ok": true,
    "value": { /* 方法返回值 */ }
  }
}
// 或
{
  "type": "server-response",
  "rpcId": "...",
  "result": {
    "ok": false,
    "error": { "code": "bad-request", "message": "...", "details": {...} }
  }
}
```

**踩坑记录**：`method` 只写在 URL 里不够，body 里也必须有，且 `type: "client-request"` 不可省。缺任何一个都返回 `bad-request: invalid client-request message`。

### 1.3 可用端点（实测）

| 端点 | 状态 | 返回 |
|------|------|------|
| `session.list` | ✅ 可用 | 会话列表（**仪表盘的主数据源**） |
| `settings.describe` | ✅ 可用 | `{ writable, hasDocument, namespaces[11] }` |
| `subagent.list` | ⚠️ 需要参数 | `bad-request: invalid payload` |
| `respond` | ⚠️ 需要参数 | 审批/提问的**应答**入口 |
| `session.get` / `jobs.list` / `goals.list` / `approvals.list` | ❌ 404 | 不存在 |

**关键结论**：没有 `approvals.list`，但有 `respond` —— 说明**审批是通过 WebSocket 推送的，不能轮询**。仪表盘必须常连 WebSocket 才能捕获"等你回答"这个最重要的状态。

### 1.5 WebSocket 事件帧（实测确认）

连接 `ws://127.0.0.1:3080/api/events.mux` 后自动订阅活跃会话，无需发送订阅消息。所有帧的外层格式：

```jsonc
{
  "type": "server-request",
  "rpcId": "7d665fc3-56b4-41b9-bc99-460abe2fa4a5",
  "method": "session/jobs",          // ★ 帧类型在 method 里
  "payload": { /* 见下 */ }
}
```

**四种实测帧类型**：

#### `session/subscribed` — 连接建立确认

```jsonc
{
  "type": "session/subscribed",
  "sessionId": "session-031d6e5f-6ac3-4176-a896-f9c7b8eff5d4",
  "lastSeq": 238500
}
```

#### `session/jobs` — ★ 后台任务列表（仪表盘 `detail` 的最佳来源）

```jsonc
{
  "type": "session/jobs",
  "sessionId": "session-031d6e5f-...",
  "jobs": [
    {
      "id": "pwsh-1",
      "kind": "pwsh",
      "label": "$env:BRIDGE_PORT='3099'\nnode bridge.js",   // 完整命令，含换行
      "status": "running",
      "startedAt": 1786841035124
    }
  ]
}
```

> **桥接处理**：取第一个 `status === "running"` 的 job，`label` 按行拆分、跳过 `$env:` 赋值行，取第一行有效命令截断到 40 字符 —— 这就是圆屏上"它正在干什么"那一行。

#### `session/event` — 会话事件流（高频，每个 token 一帧）

```jsonc
{
  "type": "session/event",
  "sessionId": "session-031d6e5f-...",
  "event": {
    "type": "assistant/chunk",      // 或 tool/call、assistant/message
    "seq": 241049,
    "time": 1786841274338,
    "data": {
      "turn": 85,
      "step": 58,
      "chunk": {
        "type": "reasoning-delta",   // block-start / reasoning-delta /
                                     // tool-call-delta / block-end / usage / finish
        "index": 0,
        "text": "Let"                // 流式增量
      }
    }
  }
}
```

已观察到的 `event.type`：`assistant/chunk`、`assistant/message`、`tool/call`  
已观察到的 `chunk.type`：`block-start`、`reasoning-delta`、`tool-call-delta`、`block-end`、`usage`、`finish`

> **桥接处理**：**故意不用**。这个流每个 token 一帧，转发到 ESP32 会淹没串口和 WiFi，且圆屏没有渲染流式文本的空间。仪表盘用 `session/jobs` 的粗粒度状态就够了。

#### `session/projection` — 投影更新推送

与 `session.list` 里的 `projections.values` 同结构，实时推送。桥接用它免去部分轮询。

### 1.6 审批帧 — 尚未捕获

在 20-30 秒的抓包窗口内**没有观察到**审批/提问帧，因为期间没有触发审批。桥接的实现方式是**宽容匹配**：

```javascript
if (/approv|permission|user-question|userQuestion|ask/i.test(method)) { ... }
```

并在命中时把完整 payload 打进日志（`ASK-SHAPED FRAME: ...`）。这样第一次真实审批发生时，日志会记录准确结构，届时可据此收紧匹配。

**已确认的相关事实**：
- `approvals.list` / `approvals.pending` 等端点**不存在**（404）
- `respond` 端点**存在**（返回 `bad-request` 而非 404，说明需要正确参数）

因此审批必然是推送式的，常连 WebSocket 是唯一途径。

## 第二部分：桥接 ↔ 固件（自定义协议）

### 2.1 传输选择

| | 选择 | 理由 |
|---|---|---|
| 传输 | **WebSocket over WiFi** | 双向、实时、ESP32 库成熟；不用 BLE 是因为 Windows 的 BLE 栈麻烦（参考项目只支持 macOS 就是这个原因） |
| 角色 | **桥接 = 服务端，固件 = 客户端** | 板子上电主动连，重连逻辑在固件侧，桥接无需发现设备 |
| 端口 | **默认 3082** | 避开 3080（DSH）和 3081（远程网关） |
| 编码 | **JSON 文本帧** | ESP32 用 ArduinoJson 解析；二进制省的那点带宽不值得增加调试难度 |

### 2.2 认证

固件连接时在 URL 携带预共享 token：

```
ws://<pc-ip>:3082/dev?token=<32 hex chars>
```

token 由桥接首次启动生成，存 `$DSH_HOME/esp32-bridge/device-token.txt`，你把它填进固件配置。**局域网内也要认证** —— 否则同网段任何设备都能读你的会话标题、发审批应答。

### 2.3 桥接 → 固件（下行）

#### `state` — 仪表盘状态（核心帧，1Hz 或变化时推送）

```jsonc
{
  "t": "state",
  "phase": "idle" | "working" | "waiting" | "done" | "error",
  "title": "询问 AI 助手身份",     // 会话标题，UTF-8，固件截断显示
  "detail": "编译 web 包",         // 当前动作（可空）
  "ctx": 78,                       // 上下文占用百分比 0-100（外环）
  "turns": 85,
  "steps": 784,
  "perm": "workspace-write",       // 权限档，决定颜色警示
  "sessions": 4,                   // 会话总数
  "running": 1,                    // 正在跑的会话数
  "seq": 227080                    // 事件序号，固件用于丢弃过期帧
}
```

`phase` 的判定规则（桥接侧计算，固件不做业务判断）：

| phase | 条件 | 圆屏表现 |
|-------|------|---------|
| `idle` | 无 running 会话，无待答 | 暗色 + 时钟 |
| `working` | 有 running 会话 | 蓝色呼吸环 + detail |
| `waiting` | 有待答审批/提问 | **黄闪 + 大字 + 按钮 + 提示音** |
| `done` | 刚从 running 变为非 running | 绿 ✓ + 完成音（3 秒后回 idle） |
| `error` | 会话报错 / 桥接与 DSH 断连 | 红 ✕ + 错误音 |

#### `ask` — 需要你决策（触发 waiting）

```jsonc
{
  "t": "ask",
  "id": "ask-7f3e9a",              // 应答时回传
  "kind": "approval" | "question",
  "title": "执行命令？",
  "body": "Remove-Item -Recurse D:\\build",   // 固件圆屏截断显示
  "options": [                      // 最多 3 个，固件渲染为按钮
    { "id": "allow", "label": "允许", "style": "primary" },
    { "id": "deny",  "label": "拒绝", "style": "danger" }
  ],
  "expiresAt": 1786840300000        // 超时后固件自动回 idle
}
```

#### `speak` — 语音播报（可选，v1.5）

```jsonc
{ "t": "speak", "text": "任务已完成" }
```

#### `beep` — 提示音

```jsonc
{ "t": "beep", "kind": "done" | "waiting" | "error" }
```

#### `pong` — 心跳应答

```jsonc
{ "t": "pong", "at": 1786840217529 }
```

### 2.4 固件 → 桥接（上行）

#### `hello` — 连接后自报身份

```jsonc
{
  "t": "hello",
  "fw": "dsh-dial/0.5.0",
  "board": "ESP32-S3-Touch-LCD-1.85B",
  "battery": 87,
  "charging": false
}
```

#### `answer` — 应答审批/提问（★ 设备存在的理由）

```jsonc
{
  "t": "answer",
  "id": "ask-7f3e9a",              // 回传 ask 的 id
  "choice": "allow"                // options[].id 之一
}
```

#### `cmd` — 控制命令

```jsonc
{ "t": "cmd", "action": "stop" }   // stop | pause | resume
```

#### `ping` — 心跳（固件每 10s 发一次）

```jsonc
{ "t": "ping", "battery": 87, "charging": false }
```

#### `sensor` — 传感器上报（可选，30s 一次）

```jsonc
{
  "t": "sensor",
  "battery": 87,
  "charging": false,
  "imu": { "shake": false }        // 摇一摇手势（v1.5）
}
```

### 2.5 连接生命周期

```
固件上电
   ↓
连 WiFi（NVS 存的 SSID/密码，失败则开热点配网）
   ↓
连 ws://<pc>:3082/dev?token=...
   ↓ 成功
发 hello  ──────────────→  桥接记录设备
   ↓                        ↓
   ←────────────────────  推 state（立即一次，之后 1Hz 或变化时）
   ↓
每 10s 发 ping  ────────→  回 pong
   ↓
收到 ask  →  黄闪+响铃+显示按钮
   ↓
用户点按钮  →  发 answer  →  桥接调 DSH 的 respond
   ↓
断线  →  1s/2s/4s/8s… 指数退避重连（上限 30s），屏幕显示 offline
```

### 2.6 诚实状态原则

> 借鉴 `angaziz/beacon`（MIT）的设计原则：**a value is shown as loading / live / stale / offline — never a guess dressed up as live data.**

固件必须区分四种数据新鲜度，不能把过期数据当实时显示：

| 状态 | 判定 | 表现 |
|------|------|------|
| `loading` | 已连接但还没收到第一帧 state | 灰色骨架 |
| `live` | 最后一帧 state 在 3s 内 | 正常颜色 |
| `stale` | 最后一帧 state 超过 3s | 数值变灰 + 小时钟图标 |
| `offline` | WebSocket 断开 | 暗屏 + 断线图标，**不显示任何数值** |

这条原则很重要：一个显示"任务进行中"但其实早就断线的仪表盘，比一个明确显示"离线"的仪表盘更糟 —— 后者你知道要去看电脑，前者会让你放心地不去看。

### 已知取舍

1. **`session/event` 不转发** —— 每 token 一帧，圆屏无处渲染，会淹没链路。仪表盘用 `session/jobs` 的粗粒度状态。
2. **`cmd` 动作是空壳** —— 本版 DSH 没有 `jobs.cancel` / `session.cancel` 端点，固件侧路径已通，主机侧待端点出现后接上。
3. **电量是占位值** —— 板上有充电管理但 I2C 上没有电量计，需要接电池分压后读 ADC。
4. **音频按 ES8311 写** —— vendored 代码来自姊妹板；本板 PCM5101 会让 `begin()` 返回 false，固件静默运行，功能不受影响。
